\section{Methodology}
\label{sec:method}

\subsection{Task Decomposition and Planning}
\label{sec:planning}

The \texttt{parse\_intent} node asks a lightweight model for a structured intent: action, target site, target and content strings, risk level and confidence. If the request contains a connective (``and'', ``then'', a comma) or more than eight words, a planning model decomposes it into steps $P=(g_1,\dots,g_n)$, each with a description, an action type and an expected outcome; a request to enter literal text becomes a single text-entry step, and anything else a one-step plan.

Execution then chooses one action per iteration. \texttt{plan\_action} gives the model the goal, the plan with the current step marked, the page title, URL and state, and the element manifest, and asks for one of \texttt{navigate}, \texttt{click}, \texttt{type\_text}, \texttt{press\_key}, \texttt{scroll}, \texttt{extract}, \texttt{complete} or \texttt{need\_help}. Deterministic rules then adjust the choice: exact-text requests are grounded to the best-scoring visible text field, repeated navigation to the current site is suppressed, and plan steps that name clicking a result, extracting or reporting are mapped to those actions. Some rules are site-specific; on Google with a search goal the agent types the query and presses Enter rather than loading a results URL directly (see Section~\ref{sec:security}).

\subsection{Grounding: DOM First, Vision on Demand}
\label{sec:grounding}

Each observation starts with a DOM pass over buttons, inputs, text areas, selects, links, elements with button or link roles, and editable regions. For each element the extractor records tag, role, accessible label, up to 120 characters of text, placeholder, type, visibility, enabled state, bounding box, and three selectors (an identifier attribute it writes into the live DOM, a CSS selector and an XPath, tried in that order). Only interactable elements are kept; they are ranked with submit-like controls first, deduplicated, limited to five links, stripped of cookie and advertising labels, and capped at 50.

The vision model is used only when the planner returns \texttt{need\_help}, by choice or because its call failed. The agent sends a screenshot and receives an action with a target point given as fractions of the 1280\,$\times$\,800 viewport, where it clicks and, if needed, types. Such actions are not checked individually; a wrong click is caught, if at all, by the completion predicate. Identical screenshot--goal pairs are served from a cache.

\subsection{Failure Classification and Recovery}
\label{sec:recovery}

A failed action is first retried through a fresh observation by the \texttt{verify} node, up to three times. Later failures go to the recovery node, which matches the error text against patterns for seven types (\texttt{captcha}, \texttt{transient}, \texttt{element\_not\_found}, \texttt{verification\_failed}, \texttt{navigation\_failed}, \texttt{vision\_needed}, \texttt{llm\_failure}) or \texttt{unknown}. A CAPTCHA ends the task as \textsc{Blocked}. Other failures are assigned a strategy from the ladder \texttt{retry} $\rightarrow$ \texttt{alternative\_selector} $\rightarrow$ \texttt{vision\_fallback} $\rightarrow$ \texttt{replan}, one level per two attempts, with type-specific shortcuts; after six attempts the task fails. Each decision is stored as a recovery record. In the current code the chosen strategy is recorded but not executed: the strategy field is not declared in the state schema and is dropped, so every non-terminal recovery re-observes and re-plans.

\subsection{Role-Based Local Model Routing}
\label{sec:routing}

A deterministic analyzer maps each call's type, text and flags to required capabilities and a role: recovery calls to a recovery model; image inputs or screen-related wording to a vision model; intent parsing and simple navigation to a lightweight model; decomposition and multi-clause requests to a planner; the rest to a general model. Each role has a configured, ordered candidate list; the defaults are small Qwen2.5, Qwen3.5 and DeepSeek-R1 models of 1.5B--7B parameters for text roles and \texttt{qwen3-vl:2b} or \texttt{moondream} for vision. The first candidate the local Ollama server reports as installed is used (the list is refreshed every 300\,s). To limit model reloads, the router keeps the active model whenever it has the required capabilities, except for recovery calls; with no installed candidate it falls back to a fallback and then a base model. A single-model mode serves as an ablation. A switch cool-down is configurable but not read by the router.


\subsection{Episodic Memory}
\label{sec:memory}

On termination, \texttt{complete} writes the outcome to SQLite and to a Chroma collection: for a success, the goal, final URL and number of model calls; for a failure, the error and URL. The retrieval side exists: a context router queries memory (and, for longer or procedural tasks, a knowledge collection), and a builder deduplicates the results and fits them into a 3{,}500-token budget inside an untrusted-content banner in the planning prompt. On the live path, however, the runner initializes the retrieved lists as empty rather than unset, which the router treats as already retrieved; memory is written but not read. Since the stored records hold no selectors or action sequences, repairing the read path is necessary but not sufficient for learning from past runs.

\subsection{Extension to Local System Access}
\label{sec:desktop}

The browser loop carries over to the desktop if the accessibility tree replaces the DOM, a window screenshot replaces the page screenshot, and typed operating-system predicates replace URL and DOM checks. Today the repository contains a desktop executor wrapping PyAutoGUI (click, type, hotkey, screenshot) and psutil (process listing); no node, action type or API route calls it, its only test checks that its methods exist, and without a display it silently returns a fixed screen size and empty screenshots. A file helper reads and writes text files but is not called by the agent and does not confine paths to its workspace. The rest of this subsection is a design (\status{Proposed}).

\paragraph{Actions and grounding} The action space covers files (list, hash, read, create, overwrite with backup, move, trash, delete), processes (list, launch an allow-listed program, terminate), applications (open, focus, close) and UI controls (invoke, set value, type, hotkey). Grounding reads the foreground window's accessibility tree (Windows UI Automation, macOS Accessibility, AT-SPI) into a manifest shaped like the DOM manifest, with names sanitized. Vision on a window screenshot is used when the tree exposes too few actionable elements or the planner asks for help, and a coordinate action counts as done only after its postcondition holds.

\paragraph{Verification} Every mutating action carries typed, exact postconditions evaluated after execution and stored with before/after values (Table~\ref{tab:desktop}). File predicates compare SHA-256 digests, sizes and modification times; process predicates identify a process by PID and creation time, which guards against PID reuse; window and accessibility predicates compare titles, focus, values and states. Read-only actions must leave a manifest of the workspace unchanged.

\paragraph{Permission tiers and enforcement} Tiers are computed from the concrete action and arguments, never from the model's risk label. T0 (observe) runs freely. T1 (reversible: the inverse is recorded, e.g., a backed-up overwrite or a move to trash) runs automatically only if the user enabled automatic approval of low-risk actions. T2 (destructive: permanent deletion, terminating a process the agent did not start, invoking controls labelled Delete, Discard, Send or Pay) and T3 (network-capable programs, password fields) always need approval; secrets are injected by the executor and never pass through the model. Paths outside allow-listed roots, credential directories, inline-code interpreters and privilege elevation are refused. A new \texttt{action\_gate} node between planning and execution applies the tier, a path jail that resolves symbolic links before the containment test, and a dry-run preview; approvals are bound to a hash of the exact action so arguments cannot change after consent. Each local action is appended to a hash-chained audit log that stores digests of arguments and state, never file contents or typed text.
