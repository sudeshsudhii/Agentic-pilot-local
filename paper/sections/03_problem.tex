\section{Problem Formulation}
\label{sec:problem}

\paragraph{Environment and actions} The environment is the user's computer, observed through one or more \emph{backends} $b$: a browser page, the desktop's windows and controls, the file system, and the process table. Its state $s_t$ is the combination of backend states, and each backend offers an observation $\Omega_b(s_t)$ (for the browser: URL, title, element list and screenshot; for the file system: path metadata and content hashes) and a set of typed actions. The planner maps a goal $g$, a plan $P=(g_1,\dots,g_n)$ and the current observation to an action $a_t$ for one backend. Executing it returns a \emph{dispatch flag} $\alpha_t\in\{0,1\}$, which says only that the call returned without error.

\paragraph{Completion} The agent may report a task complete only when a completion predicate holds on the state observed \emph{after} the action:
\begin{equation}
\Phi(g,s_{t+1},P,\sigma) = \textstyle\bigwedge_{c\in C(g,P)} c(s_{t+1}) \;\wedge\; \pi(P) \;\wedge\; \neg\beta(s_{t+1},\sigma),
\label{eq:phi-general}
\end{equation}
where $C(g,P)$ is the set of postconditions that the goal and plan steps imply, $\pi(P)$ states that no plan step is pending, and $\beta$ is a blocking or safety condition: a challenge page, an unapproved high-risk action, or a policy violation, with $\sigma$ the approval and policy state. Dispatch success does not imply completion, $\alpha_t=1\not\Rightarrow\Phi=1$. Every evaluation of $\Phi$ is stored with the observed values it used, so that a reported completion can be audited later.

\paragraph{The implemented browser predicate} For the browser, $C(g,P)$ is derived from the wording of the request rather than from typed postconditions. The implemented $\Phi$ is the conjunction of: no browser-error URL, error or ``not found'' title, or redirect to a sign-in page that the request did not name ($E$); not still on a search engine's home page when a search, an extraction or a multi-step plan was requested ($H$); a results page carrying the query quoted in $g$ ($Q$); the literal text that $g$ asks to be entered present in an input, exactly if $g$ says ``exactly'' ($T$); for extraction requests, an answer or structured extraction that mentions a content word of $g$ ($X$); and, for multi-step plans, no pending step unless a structured extraction exists ($R$). Each conjunct is instantiated only when its trigger occurs, so for a request that triggers none, $\Phi$ reduces to $\neg E$. A separate pre-check implements $\beta$ for bot-check pages and halts the task as \textsc{Blocked}. The per-step postconditions are weak: a step counts as done when an action other than \texttt{complete} dispatches during it. $\Phi$ is evaluated when the planner emits \texttt{complete}, when the plan index reaches $n$, or when a requested text entry has dispatched; for one-step plans this is after every successful action. A rejected evaluation returns control to observation and planning until a budget of $K=15$ planner-side model calls is spent.

\paragraph{Grounding order} Actions should be grounded in the most structured description available: typed state (file metadata, process table), then the DOM or the accessibility tree, then application metadata such as window titles, then a screenshot interpreted by a vision model, and finally a person. The browser backend implements DOM grounding, screenshot-based vision fallback and human hand-off for CAPTCHAs and approvals; accessibility-tree, metadata and typed-state grounding belong to the proposed computer backend.

\paragraph{Metrics} Let $\mathcal{T}_c$ be the episodes reported complete, and $\Phi^{\star}$ an independent oracle that the experimenter writes per task. The false completion rate is
\begin{equation}
\mathrm{FCR} = \lvert\{\tau\in\mathcal{T}_c : \Phi^{\star}(\tau)=0\}\rvert \,/\, \lvert\mathcal{T}_c\rvert,
\label{eq:fcr}
\end{equation}
and the false rejection rate (FRR) is the fraction of episodes with $\Phi^{\star}=1$ that the agent does not report complete. FCR alone rewards an agent that never finishes, so the two are always reported together with task success.
