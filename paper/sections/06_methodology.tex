\section{Evaluation Methodology}
\label{sec:method}

The evaluation comprises two completed studies: (i) component-level \textsc{actual} experiments on the implementation without a language model (gate study, ablation, latency, retrieval ranks, recovery classification, 70 control-loop episodes with a scripted stand-in model for the egress test, and 114 scripted trajectories for oracle validation); and (ii) seeded \textsc{synthetic} computational experiments that propagate those measurements through the agent's control flow under stated assumptions. Study (i) validates components; study (ii) shows what the components imply for the full agent under the assumptions. The gate study ran on 2026-10-04 on a Linux container (4-core Xeon at 2.1\,GHz, no GPU) with Python~3.11.15, Playwright~1.56.0, Chromium~141, LangGraph~1.2.12 and Chroma~1.5.9 (versions pinned in \texttt{requirements-paper.lock}); decisions of the code before the fixes come from the same script run against commit \texttt{08653e2}. Scripts, seeds and raw outputs are in the repository.

\subsection{Gate Study}
\label{sec:method-gate}

\paragraph{States and splits} A state is a goal, a URL, an HTML document served through Playwright request interception, the agent's answer and plan state where relevant, and an oracle label. Every state ends with a dispatched action, so a dispatch-only rule accepts all of them. The \emph{design} set (38 states in six categories) was used to find the gate's defects and design the fixes. \emph{Held-out~1} (12 states) was written after the fixes and not used to change them. \emph{Held-out~2} (42 states, 22 unsatisfied) was written to a fixed procedure with varied user phrasings and committed (\texttt{b9d5088}, SHA-256 recorded) before the gate was run on it; the code it was run on (\texttt{55ac1ea}) adds only default-off switches, a separate self-verification method, the loopback check and logging to the frozen gate.

\paragraph{Locality test} The 10 development tasks were run under 7 configurations through the real control loop and Chromium against a scripted stand-in for the Ollama API on 127.0.0.1, with a \texttt{sitecustomize} module logging every socket connection attempt of the harness's Python processes (\texttt{run\_egress.py}; raw logs in \texttt{artifacts/results}). The stand-in returns fixed answers and performs no inference.

\paragraph{Oracle} The label $\Phi^{\star}$ of a state states whether the goal is achieved by the page and answer shown, judged from the page's facts (for example, whether the answer contains the year in the article). It was written together with the state, before the state was judged by the gate, and it is computed by no code shared with $\Phi$. All states and labels were written by the AI agent that also designed the gate fixes (Acknowledgment); no person has relabelled them, so no inter-annotator agreement exists.

\paragraph{Modes and statistics} Each state is judged by the pre-check and $\Phi$ called directly, and by the real verification node (database, browser-pool and evidence I/O stubbed) with an empty or a generic one-sentence planner reasoning. For the ablation, each conjunct of $\Phi$ is removed in turn by a configuration switch, and the pre-check $\beta$ is skipped by an argument of the study script; the ablation runs on the predicate called directly. Counts carry Wilson and Clopper--Pearson 95\% intervals~\cite{wilson1927probable,clopper1934use}; comparisons on the same states use the exact McNemar test~\cite{mcnemar1947note} on paired decision correctness. Against the dispatch-only rule the discordant pairs are the withheld unsatisfied states (only the gate is correct) and the rejected satisfied states (only dispatch is correct). Latency is the median of 20 repetitions after a warm-up.

\subsection{End-to-End Evaluation Harness}
\label{sec:method-e2e}

For task-level evaluation of the full agent, which lies outside the present study, we release a harness (Supplement, Section~\ref{sec:method-e2e-full}). It runs 40 tasks (10 development, 30 test) on five self-hosted sites with fictional content, at four difficulty tiers, under the full system, two baselines (no completion check; self-verification by the planner model) and one-factor ablations, with three trials per task at temperature 0. Its oracle $\Phi^{\star}$ uses only server-side records, the final URL and ground-truth facts, which $\Phi$ does not read.

\subsection{Simulation and Evidence Classes}
\label{sec:sim}

\paragraph{Why simulation} The evaluation focuses on component-level validation and simulation-based analysis under controlled experimental conditions. Simulation is appropriate for the agent-level questions because they depend on component behaviour that can be measured without a model (detection and false-rejection rates of $\Phi$, latencies, the recovery engine's classification, retrieval ranks) and on planner behaviour that cannot; propagating the first through the control flow of the loop while sweeping the second shows which unmeasured parameters decide H1--H5. The seeded simulation (\texttt{benchmarks/simulation}) does not execute the agent.

\paragraph{Evidence classes} Every number in this paper belongs to one of six classes: \textsc{actual} (executed or measured on the implementation), \textsc{synthetic} (produced by the simulation), \textsc{assumed} (an input value chosen by us), \textsc{derived} (computed from existing results), \textsc{literature}, or \textsc{proposed} (a designed component that is not implemented). Numbers in Sections~\ref{sec:results} and~\ref{sec:safety} are \textsc{actual} unless stated, and numbers in Section~\ref{sec:sim-results} are \textsc{synthetic} unless marked; captions state the class of table values.

\paragraph{Design} The simulation draws 100 scenarios (seed 202), each with a task category and an outcome class that sets whether the goal is met. Detection and false-rejection rates are derived from the held-out gate states, latencies are resampled from component measurements, and planner behaviour is assumed: chiefly the probability $\pi=0.65$ that a point at which the code evaluates $\Phi$ is reached while the task is unfinished (a \emph{claim}), swept from 0.3 to 0.95. Comparisons are paired by scenario. \emph{Policy-level} outcomes describe how an episode ends; \emph{decision-level} outcomes compare the verifier's first decision on a claim with the true state at that claim, the only level at which verifiers share one ground truth. Monte Carlo replications regenerate 1{,}000 scenario sets with rates drawn from their Beta posteriors. Every synthetic $p$-value and interval is conditional on the assumptions. Details are in the Supplement (Sections~\ref{sec:sim-full} and~\ref{app:simparams}).

\paragraph{Post-hoc revision} Parameters and code of the first model (v1) were committed (\texttt{3a0aa8e}) before the scenario set was generated. An audit then found that v1 contradicted the implementation in four places (false-rejection rates taken from bot-check pages, no re-check after a continuation, a basic detector that did not fail closed, recovery applied to every failure); the reported model, v2, fixes them and was revised once more to match the code's recovery paths. v2 was written after the v1 results were known and is \emph{not pre-registered}; the corrections moved the results in favour of $\Phi$ (task success relative to no verification from 37 against 43 to 44 against 46). v1 outputs and every changed number are archived.
