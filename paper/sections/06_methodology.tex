\section{Evaluation Methodology}
\label{sec:method}

Three evaluations are reported, with different scope: (i) component-level \textsc{actual} measurements on the implementation without a language model (gate study, ablation, latency, retrieval ranks, recovery classification, 70 control-loop episodes with a scripted stand-in model for the egress test, and 114 scripted trajectories for oracle validation); (ii) a seeded \textsc{synthetic} simulation of the full agent built on those measurements and stated assumptions; (iii) an end-to-end protocol with a language model, implemented but not executed. Only (iii) would validate the full agent; (i) validates components and (ii) shows what the components imply under the assumptions. The component experiments need no language model. The current-code results were produced on 2026-10-04 on a Linux container with a 4-core Intel Xeon at 2.1\,GHz, 15\,GiB RAM and no GPU, with Python~3.11.15, Playwright~1.56.0, headless Chromium~141 and LangGraph~1.2.12; the decisions of the code before the fixes come from runs on a similar container (2026-09-30 to 2026-10-01) of the study script against the agent code of commit \texttt{08653e2}, checked out separately, and are deterministic. Scripts, seeds and raw outputs are under \texttt{artifacts/} and \texttt{benchmarks/e2e/} in the repository.

\subsection{Gate Study}
\label{sec:method-gate}

\paragraph{States and splits} A state is a goal, a URL, an HTML document served through Playwright request interception, the agent's answer and plan state where relevant, and an oracle label. Every state ends with a dispatched action, so a dispatch-only rule accepts all of them. The \emph{design} set (38 states in six categories) was used to find the gate's defects and design the fixes. \emph{Held-out~1} (12 states) was written after the fixes and not used to change them. \emph{Held-out~2} (42 states, 22 unsatisfied) was written to a fixed procedure---varied user phrasings per category, including wordings the gate's trigger lists do not contain, with a balanced split---and committed before the gate was run on it; the gate was then run on a working tree committed as \texttt{55ac1ea}, which adds to the frozen gate code only configuration switches for the ablation, a separate self-verification baseline method, the loopback endpoint check and extra logging; none of them is on by default or changes the gate's default decisions (diff \texttt{b9d5088..55ac1ea}). Its SHA-256 is recorded in the repository.

\paragraph{Locality test} The 10 development tasks were run under 7 configurations through \texttt{run\_e2e.py} against a scripted stand-in for the Ollama API (\texttt{fake\_ollama.py}, 127.0.0.1:11435), with \texttt{benchmarks/e2e/egress} on the Python path so that its \texttt{sitecustomize} module logs every socket connection attempt to the file named by \texttt{PILOT\_EGRESS\_LOG}. The raw log, the episode records, the configurations and the reconstructed command are released in \texttt{artifacts/results/e2e\_smoke\_stub}, and \texttt{summarize\_egress.py} rebuilds the summary.

\paragraph{Oracle} The label $\Phi^{\star}$ of a state states whether the goal is achieved by the page and answer shown, judged from the page's facts (for example, whether the answer contains the year in the article). It was written together with the state, before the state was judged by the gate, and it is computed by no code shared with $\Phi$. Its limitation is that all states and labels were written by the AI agent that also designed the gate fixes (Acknowledgment) and no person or second annotator has relabelled them, so no inter-annotator agreement exists; a protocol for independent relabelling with Cohen's $\kappa$~\cite{cohen1960coefficient} is in the repository.

\paragraph{Modes and statistics} Each state is judged by the pre-check and $\Phi$ called directly, and by the real verification node (database, browser-pool and evidence I/O stubbed) with an empty or a generic one-sentence planner reasoning. For the ablation, each conjunct of $\Phi$ is removed in turn by a configuration switch, and the pre-check $\beta$ is skipped by an argument of the study script; the ablation runs on the predicate called directly. Counts carry Wilson and Clopper--Pearson 95\% intervals~\cite{wilson1927probable,clopper1934use}; comparisons on the same states use the exact McNemar test~\cite{mcnemar1947note} on paired decision correctness. Against the dispatch-only rule the discordant pairs are the withheld unsatisfied states (only the gate is correct) and the rejected satisfied states (only dispatch is correct); an earlier version tested the withheld count alone and is corrected here. Latency is the median of 20 repetitions after a warm-up.

\subsection{End-to-End Harness}
\label{sec:method-e2e}

\paragraph{Environment and tasks} Live websites change and block automated traffic, and WebArena-style site images were not available offline, so we built five self-hosted sites served on the loopback interface with fictional content that a model cannot answer from memory: a search engine, an encyclopedia, a shop with search and cart, a town-office contact form and newsletter, and a notes application; a further path redirects to a sign-in wall. The 40 tasks (10 development, 30 test) cover search, navigation, text entry, extraction, form submission, multi-step tasks and 5 unsatisfiable requests, at four difficulty tiers by the number of actions a solution needs (1, 2--3, 4--6, more). The notes site appears only in the test split. Tasks needing an account, payment, a CAPTCHA, the live web, or an outcome that neither server state nor answer text can verify were excluded by design. Because the search-home check $H$ recognizes only public search engines, it never fires on these sites; its ablation in the harness is uninformative.

\paragraph{Oracle} $\Phi^{\star}$ is computed from signals that neither the agent nor $\Phi$ uses: server-side records of the sites (cart contents, form submissions, saved notes, field values autosaved by page scripts), the final URL, and the ground-truth facts in the site data matched against the agent's answer; unsatisfiable tasks are never achieved. It calls no model and shares no code with the verifier. We measured its error rate on 114 scripted trajectories driven directly through Playwright without the agent: a correct solution for each task, an idle trajectory that only opens the start page, and a near miss for 34 tasks (wrong value, wrong item, extra submission, partial query).

\paragraph{Protocol} Table~\ref{tab:e2e} (Appendix~\ref{app:tasks}) lists the configurations: the full system, two baselines---(a) no completion check and (b) self-verification by the planner model---and one-factor ablations of each conjunct, memory, recovery and each recovery strategy. Each configuration runs in its own process with its own database and memory store, at temperature 0 with a fixed seed, three trials per task, and the same budget of 15 planner calls (after which the recovery engine may grant its remaining attempts). Per episode the harness records the oracle verdict, the agent's status, browser actions, model calls and tokens, wall-clock time, each verification decision with its latency, recovery strategies, retrieved memories, Ollama version and model digests, and the host of every page request Playwright reports. The analysis reports success, FCR and FRR with Wilson intervals, per-category breakdowns, exact McNemar tests and task-level bootstrap intervals~\cite{efron1979bootstrap} for differences to the full system, and the overhead of $\Phi$ relative to baseline (a). A published agent framework as a third baseline would need its own model and prompts and is outside the scope of this paper.


\subsection{Simulation-Based Evaluation and Data Provenance}
\label{sec:sim}

\paragraph{Why simulation} The end-to-end protocol needs local model weights, which the environment used for this paper could not download. A simulation is appropriate for the remaining questions because the quantities they depend on separate into component behaviour that we can measure without a model (detection and false-rejection rates of $\Phi$, latencies, the engine's classification, retrieval ranks) and planner behaviour that we cannot; propagating the first through the control flow of the loop, while sweeping the second, shows which unmeasured parameters decide H1--H5. We built such a seeded simulation (\texttt{benchmarks/simulation}). The simulation does not execute the agent. Its outputs follow from measured and assumed inputs. Every number in this paper belongs to one of six classes: \textsc{actual} (genuinely executed or measured on the implementation), \textsc{synthetic} (produced by the simulation), \textsc{assumed} (an input value chosen by us, not measured), \textsc{derived} (computed from existing results, e.g.\ a rate estimated from actual counts), \textsc{literature} (taken from cited work), or \textsc{proposed} (behaviour of a component that is not implemented, or an evaluation not yet done). Tables and figures state the class of their values in the caption or row label; in the text, numbers in Sections~\ref{sec:results} and~\ref{sec:safety} are \textsc{actual} unless stated, and numbers in Section~\ref{sec:sim-results} are \textsc{synthetic} unless marked otherwise. An evidence ledger lists every simulated value in the main tables with its source and class.

\paragraph{Measured inputs} Without a model we measured, on the implementation (2026-10-23, 4-core Intel Xeon at 2.8\,GHz, same software versions): the decisions of $\Phi$ and of a basic success detector (error check $E$ only) on the 92 gate states; the latency of navigation, clicks, form filling, DOM extraction, screenshots and $\Phi$ on the self-hosted sites (30 repetitions each); the failure class and strategy sequence that the real recovery engine assigns to six failure messages; and the ranks at which the real Chroma memory store returns relevant records for ten queries over a 22-record synthetic memory corpus. Detection rates used by the simulation are derived from the two held-out gate sets only (for detection, the 22 unsatisfied states left after the bot-check category is excluded, 18 from held-out~2 and 4 from held-out~1; the 24 satisfied states of the same categories for false rejection), with the estimator $(k+0.5)/(n+1)$, which gives a small nonzero rate (0.07--0.13) where none was observed, as for basic detection in five categories and $\Phi$ on extraction, and turns the 0 of 24 false rejections into 0.02. Simulated categories map to gate categories as follows: navigation, search, extraction and multi-step to themselves, data entry to text entry, and form submission to text entry and multi-step pooled. The detection rate of a missing confirmation is proxied by the multi-step rate (an assumed proxy; 3 states), and the category mapping above is likewise assumed.

\paragraph{Assumptions and generation} What needs a model---how often the planner claims completion of an unfinished task, how often actions fail and are recovered, how much memory helps---is assumed and listed with its class in Table~\ref{tab:sim-params} (Appendix~\ref{app:simparams}). A \emph{claim} in the simulation stands for any point at which the code evaluates $\Phi$: a \texttt{complete} action, any successful action on the last plan step (for a request that is not decomposed, every successful action), or the typing of requested exact text; $\pi$ is the probability that such a point is reached while the task is unfinished. A scenario has a task category (navigation, search, form submission, data entry, extraction, multi-step) and an outcome class (successful, incomplete, incorrect action, missing evidence, contradictory evidence, stale evidence, ambiguous) that sets the probability that the goal is actually met. Each scenario draws its random numbers once, and every configuration reuses them, so comparisons are paired by scenario. The true outcome is evaluated per configuration because memory and continuation after a rejection change the final state. For v1, parameters and code were committed (\texttt{3a0aa8e}) before the held-out set (seed 202, 100 scenarios) was generated; the reported results come from the post-hoc v2 described below; a development set (seed 101) was used only to debug the code. After the freeze, one function was changed: the latency model (Study~F) did not give all configurations the same random draws, so it was corrected to common random numbers in \texttt{41a6097}; Studies A--E and H were not affected and gave identical outputs before and after. Later, \texttt{episode()} gained three output fields (claim, true state at the claim, first decision) for the decision-level analysis; outputs were otherwise byte-identical.

\paragraph{Corrected model (v2, post hoc)} A methodology audit of the frozen model (v1) found that it contradicted the implementation in four places: its false-rejection rates came from bot-check pages, a category the scenarios do not contain; a rejected claim followed by a successful continuation was accepted without a second check, although the verification node checks every claim; the basic detector did not fail closed on an unreadable page, although it shares the error check $E$; and recovery was applied to every action failure, although action errors are first retried three times inline and a missing confirmation reaches the recovery engine only as a budget failure after 15 model calls. The results reported here come from a corrected model, v2 (\texttt{simulate\_v2.py}), that fixes these four points, draws derived rates from their Beta posteriors in the Monte Carlo replications, adds re-planning to the latency model and sweeps the continuation rate. v2 reuses v1's generator, seeds, scenario set and assumed values. It was written after the v1 results were known and is therefore \emph{not pre-registered}; the corrections moved the results for $\Phi$ in its favour (task success relative to no verification from 37 against 43, $p=0.07$, to 44 against 46; decision accuracy from 45/71 against 43/71 to 52/74 against 46/74), mainly because v1's false-rejection rate (0.089) came from bot-check pages; v1's outputs are archived (\texttt{out/heldout\_v1}) and every number that changed is listed in the statistical correction report (\texttt{artifacts/results/final\_audit/}). Monte Carlo replications regenerate the scenario set 1{,}000 times and draw the derived rates from their posteriors, to show the variability the generator and the rate uncertainty induce; the assumed values and the recovery probabilities taken from Study~E are held fixed, so the intervals omit their uncertainty.

\paragraph{Metrics} With TP, FP, FN, TN the confusion counts of reported completion against the true outcome over $N$ scenarios: $\mathrm{TSR}=\mathrm{TP}/N$; FCR and FRR as in Eq.~\eqref{eq:fcr}, so that precision $=1-\mathrm{FCR}$ and recall $=1-\mathrm{FRR}$; F1 and accuracy $(\mathrm{TP}+\mathrm{TN})/N$. Recovery success is recovered over recoverable failures; retrieval quality is precision and recall at $k=3$ and the mean reciprocal rank (MRR) of the first relevant record. Episode time is decomposed as
\begin{equation}
T = T_{\mathrm{inf}} + T_{\mathrm{browser}} + T_{\mathrm{evidence}} + T_{\mathrm{verify}} + T_{\mathrm{recovery}},
\label{eq:time}
\end{equation}
with browser, evidence and $\Phi$ times resampled from the measurements and inference time assumed. Two levels are kept apart. \emph{Policy-level} outcomes describe how an episode ends (task success, episode-level false completion); \emph{decision-level} outcomes describe whether the verifier's first decision on a completion claim matches the true state at that claim. Because a rejection can change how an episode ends, the final ground truth of a scenario may differ between configurations, so only the decision level compares verifiers against one shared truth. The decision-level outcome was defined after the v1 results were known, when an audit showed that the earlier accuracy comparison mixed the two levels. Paired configurations are compared by the exact McNemar test on per-scenario binary indicators of one level, and the variability of paired differences across regenerated scenario sets by Monte Carlo percentiles. Every $p$-value and interval computed from synthetic data is conditional on the simulation assumptions; it describes the synthetic sample, not the deployed agent.

\paragraph{Studies} Study~A generates the scenarios and computes the completion metrics, B compares four completion rules, C ablates components, D evaluates memory, E recovery, F overhead, G privacy (analytically, Section~\ref{sec:safety}) and H sensitivity.

\paragraph{Validation by recomputation} For v1, a separate AI agent of the same authoring pipeline, given only the per-scenario output files, recomputed, with separately written code, the confusion counts, rates and paired tests of Studies B and C and the memory and recovery statistics from the per-scenario files, and found no discrepancy (\texttt{simulation\_validation\_report.md}). Monte Carlo, sensitivity, latency, decision-level and recovery paired-test values were not independently recomputed. This check is a recomputation of the analysis code's arithmetic from the same synthetic files; it is neither independent human annotation of any label nor an independent replication of an experiment. For v2, a final AI review agent of the same pipeline recomputed with separately written code the policy- and decision-level confusion counts, the paired tests and the recovery and memory values from the per-scenario files, reran the simulation and the table generator byte for byte, and found no discrepancy; Monte Carlo, sensitivity and latency values were checked only through that rerun. It also found that v2 first sent requests for help and failed navigations to the recovery engine without the retries the code makes; this was corrected before the values reported here.
