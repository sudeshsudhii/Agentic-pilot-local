\section{Introduction}
\label{sec:intro}

Computer-use agents operate software for a person: they open pages and applications, type into fields, move files and read results~\cite{xie2024osworld,zhang2025ufo,agashe2025agents}. Many current agents send each observation, often a full screenshot, to a hosted multimodal model~\cite{he2024webvoyager,zheng2024seeact,zhang2025ufo,zhang2025appagent}. For a personal assistant this is a poor fit, because a logged-in screen carries names, messages and account data, and leakage of personal information from language models has been measured even after scrubbing~\cite{lukas2023pii}.

A second problem is independent of where the model runs: an agent can believe it has finished when it has not. We call this \emph{premature completion}, a terminal ``done'' while the environment does not satisfy the goal. In a browser, the agent opens the search engine and stops before issuing the query; on a desktop, it reports a file as saved when the file was written elsewhere, or a program as closed when it is still running. Each individual action succeeded; the task did not. Benchmarks that check the final environment state show how often agents fail~\cite{zhou2024webarena,xie2024osworld}, and asking the model to judge itself is not a reliable remedy~\cite{huang2024cannot}. The stakes grow with the environment: a premature ``done'' on a web search wastes time, while on a file system it can hide lost data.

Agentic Pilot is an open-source agent built around one rule: \emph{a successfully executed action is not a successfully completed task}. The agent observes the environment, plans and grounds an action, executes it, observes the result, and may report completion only when a check on the observed state passes; the inputs to that check are kept as evidence. Its models run locally through Ollama, and its control loop is an explicit LangGraph state machine. We use \emph{autonomous} in the sense that the agent plans and acts without step-by-step instructions while still handing high-risk tasks and CAPTCHAs to the user, and \emph{privacy-preserving} in the specific sense that, by default, no prompt or screenshot leaves the machine for a model provider (Section~\ref{sec:safety} states what this does not cover). The implemented execution environment today is a Chromium browser driven by Playwright. We are extending the agent to the rest of the computer, including desktop applications, windows, files and processes, and this paper describes that direction with a strict separation between what is implemented, what is a prototype, and what is a design.

We make the following contributions:
\begin{enumerate}
\item A problem formulation of evidence-gated completion that separates action dispatch from task completion across execution environments, with a completion predicate over observed state, expected postconditions, task progress and safety state, and the false completion and false rejection rates used to measure it (Section~\ref{sec:problem}).
\item An architecture that separates the observe--plan--act--verify loop from the execution backend, with an implemented browser backend (DOM-first grounding, vision fallback, CAPTCHA halting, per-action evidence) and a proposed computer backend (accessibility-tree grounding, typed postconditions, deterministic permission tiers); today the loop's observation and execution nodes are bound to the browser (Section~\ref{sec:arch}).
\item A code-level audit of which capabilities are implemented, integrated, tested and evaluated, and the fixes it led to (Section~\ref{sec:impl}).
\item A component study of the browser completion gate on 38 constructed end states and 12 held-out ones, inside the live verification node, before and after those fixes (Section~\ref{sec:results}), and an evaluation protocol for computer-use tasks whose browser part the repository's evaluation harness can already run (Section~\ref{sec:method}).
\end{enumerate}

We do not claim an evaluated computer-use agent. The computer backend is a prototype that is not connected to the control loop, and no end-to-end task with a language model has been measured. Section~\ref{sec:related} reviews related work, Section~\ref{sec:problem} states the problem, Sections~\ref{sec:arch}--\ref{sec:impl} describe the system, Sections~\ref{sec:method}--\ref{sec:discussion} the evaluation, and Sections~\ref{sec:safety}--\ref{sec:conclusion} safety, limitations and future work.
