\section{Experimental Setup}
\label{sec:setup}

\subsection{Component Studies}

The gate and router studies need neither a language model nor network access and were run for this paper on a Linux container with a 4-core Intel Xeon at 2.8\,GHz, 15\,GiB RAM and no GPU, using Python~3.11.15, Playwright~1.56.0 with headless Chromium~141.0.7390.37 and LangGraph~1.2.12, on agent code before (\texttt{2361d50}) and after (\texttt{eb3803e}) the fixes. The scripts are under \texttt{artifacts/experiments/} in the repository.

\paragraph{Gate study} We built 38 terminal browser states in six categories (Table~\ref{tab:gate}), including two satisfied states that resemble bot checks and one request whose wording triggers no conjunct, and used them to find the gate's defects and to design the fixes. We then wrote 12 further held-out states, not used for the fixes, several aimed at the new checks' weak spots. Each state has a goal, a URL, an HTML document served for it by Playwright request interception (no network traffic), the answer and plan state where relevant, and an oracle label $\Phi^{\star}$ with a rationale. Every case ends with a dispatched action, so a dispatch-only rule accepts all of them. We judge each state with the pre-check and \texttt{verify\_task\_completion} called directly (component), and with the real \texttt{verify} node, its database, browser-pool and evidence I/O stubbed, on the state the graph would hold after the final action, with an empty or a generic one-sentence planner \texttt{reasoning} (live). Latency is the median of 20 repetitions of the component decision after a warm-up. We wrote all cases and labels ourselves, so the rates describe coverage, not expected performance, and the post-fix design-set rates are optimistic by construction.

\paragraph{Routing study} We marked models as installed in the registry and called the router with each call site's arguments, in isolation and in the agent's call order with the previous selection as the active model.

\paragraph{Task suite} The repository's eight benchmark tasks include four without a checkable criterion. We propose 30 tasks, five in each of six categories: navigation, search, form text entry, extraction of a known fact, two- to three-step tasks, and blocking or error conditions (a public CAPTCHA demonstration page, HTTP error endpoints). Each has an oracle $\Phi^{\star}$ written before any run and applied to the retained page or the saved final screenshot by a person blind to the agent's reported status. \todo{AUTHOR: finalize and publish the 30 tasks and oracles.}

\paragraph{Configurations} All are presets of the repository's ablation runner (\texttt{python main.py --eval}): (i)~full system; (ii)~no gate, which accepts every completion claim; (iii)~no recovery; (iv)~vision-only grounding, which withholds the element manifest from the planner while $\Phi$ keeps DOM access; (v)~single model; and (vi)~no memory.

\paragraph{Metrics} Success rate under $\Phi^{\star}$; FCR (Eq.~\ref{eq:fcr}) and false-rejection rate; model calls and executed actions; wall-clock time; recovery success (recovered tasks that end satisfied); vision-invocation rate; and evidence completeness (executed actions with both screenshots and an execution record, and completed tasks with a completion screenshot). Rates carry Wilson 95\% intervals over task--trial pairs.
