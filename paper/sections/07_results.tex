\section{Results}
\label{sec:results}

All results concern the browser backend and its components. None measures end-to-end task success.

\subsection{Completion Gate (G1)}
\label{sec:res-gate}

\input{tables/gate_results}

Table~\ref{tab:gate} reports the gate study. On the code before the fixes, the pre-check and $\Phi$ withheld 15 of the 23 unsatisfied design states and rejected 3 of the 15 satisfied ones; inside the live verification node they withheld only 14 (empty planner reasoning) or 13 (verbose reasoning), because the node let a premature \texttt{complete} mark a pending step done and took the planner's reasoning for an answer. After the fixes all three modes agree on every state of every set. On the design states the gate withholds 20 of 23 and rejects 1 of 15, and corrects 7 states relative to the earlier gate without breaking any; we report these counts without significance tests, because the fixes were designed on these states and a test of them would be circular.

The held-out sets give the honest estimate. On held-out~2, frozen before testing, the gate withholds 9 of 22 unsatisfied states (0.41; 95\% interval 0.23--0.61) and rejects 1 of 20 satisfied ones (0.05; 0.01--0.24), so it is correct alone on 9 states and wrong alone on 1 (exact McNemar $p=0.021$); pooled with held-out~1, it withholds 11 of 27 (0.25--0.59) and rejects 2 of 27 (0.02--0.23; 11 against 2, $p=0.022$). On held-out~1 alone (2 against 1) the test has no power ($p=1.0$). Its misses follow from the rules. The answer check $X$ is triggered by words such as ``extract'' and ``information about'', so requests phrased ``tell me'', ``what year'', ``find'' or ``get me'' are not checked at all, and when $X$ fires it accepts any answer that repeats a goal term (``Tokyo is the capital of Japan'' for the population of Tokyo): none of the 5 unsatisfied extraction states is withheld. Text-entry requests phrased ``write \dots{} in'' or ``fill \dots{} with'' are not parsed; error pages titled ``410 Gone'' or ``Something went wrong'', a redirect to a different page, a press-and-hold human check, a results page for another query requested as ``Google `\dots'\,'', and an add-to-cart click that added nothing all pass. The one false rejection is a page that merely mentions reCAPTCHA. Hand-written rules thus fix the cases they were written for and generalize only partially, which answers G1 with a qualified yes: the gate withholds a significant share of premature completions, with a false-rejection rate whose 95\% upper bound is 0.24, but far fewer than on the states it was designed on.

\subsection{Contribution of Each Conjunct (G2)}
\label{sec:res-ablation}

\input{tables/ablation}

Table~\ref{tab:ablation} removes one conjunct at a time. On the design states every removal raises false completions, most for the error check $E$ (3$\to$8) and the search-home check $H$ (3$\to$7), but with 23 unsatisfied states no single removal reaches $p<0.05$ ($p\geq0.06$), which with so few states is not evidence that a conjunct is unnecessary. On the held-out sets each removal changes at most three decisions, and removing $Q$ or $X$ changes none: these conjuncts rarely fire on phrasings they were not written for. Only two removals trade false completions for false rejections: the bot-check halt $\beta$ (held-out~2: 13$\to$15 FC, 1$\to$0 FR) and, on the design states, the answer check $X$ (3$\to$6 FC, 1$\to$0 FR). Evidence types thus contribute on the states that trigger them, and the gate's coverage, not the strength of any single check, limits it.

\subsection{Overhead}
\label{sec:res-overhead}

$\Phi$ makes no model call and no browser action; it reads the page through the browser protocol. Over the 83 decisions that evaluate $\Phi$ the median latency was 26.8\,ms (90th percentile 29.5\,ms, 95th 30.3\,ms, maximum 34.6\,ms; percentiles of per-state medians of 20 repetitions, which understate the tail of single decisions), and decisions stopped by the pre-check took at most 13.4\,ms. Its added tokens and API cost are zero; the added steps that a rejection causes can only be measured end to end (Section~\ref{sec:res-e2e}).

\subsection{Locality (G3) and Oracle Validity}
\label{sec:res-privacy}

To test locality we ran 70 agent episodes (the 10 development tasks under 7 configurations, six with memory enabled) through the real control loop and Chromium against the local sites, with a scripted stand-in for the Ollama API on 127.0.0.1:11435, on an uncommitted working tree based on commit \texttt{1435fe9} (recorded in the run's metadata). We logged every outbound \texttt{connect} call made from the harness's Python processes; the Playwright driver, Chromium, the model server and DNS lookups were not instrumented. All 555 attempts went to 127.0.0.1, all to the stand-in's port, and every page request that Playwright reported named host 127.0.0.1; WebSockets and browser-internal traffic were not observed. Because the stand-in claims completion at once, the episodes made no browser action beyond the first navigation, never called the vision model and never retrieved documents; memory retrieval returned at least one record in 54 of the 60 memory-enabled episodes. The stand-in always claims completion, so these episodes say nothing about task success. The repository's test suite runs a reduced version of this check (three development tasks, one configuration, memory and retrieval disabled), together with tests that a remote model address is refused and that Chroma telemetry is off; 144 of its 147 tests pass; the 3 failures need live websites or a running local model.

The end-to-end oracle agreed with the intended verdict on all 114 scripted trajectories: no false negative among 37 achieved trajectories (95\% interval 0--0.09) and no false positive among 77 unachieved ones (0--0.05). The trajectories were written by the oracle's author, so this bounds the oracle's errors on anticipated behaviors only.

\subsection{End-to-End Evaluation}
\label{sec:res-e2e}

We have not run the end-to-end evaluation with a language model: the environment used for this paper could not download model weights. Consequently this paper makes no claim about task success, about the gate's effect on success or on false completions of the full agent, about the baselines, or about the contributions of memory, retrieval and the recovery strategies; Table~\ref{tab:status} marks these components as unevaluated. The harness, task set and analysis that produce these measurements are released and run with one command on a machine with Ollama.
