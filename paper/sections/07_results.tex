\subsection{Completion Gate on Constructed End States}

Table~\ref{tab:gate} reports the gate study. Of the 22 end states that do not satisfy their goal, the gate withholds completion in 15: all three search-engine home pages, all three pages with an HTTP error code in the title, three of the four bot-check pages (halted as \textsc{Blocked}), an empty and a wrong text field, three incomplete extraction answers including one produced while still on the search home page, and a plan with a pending step. The dispatch-only rule reports all 22 as complete. Among the 13 satisfied end states, the gate rejects one.

The FCR values in Table~\ref{tab:gate} depend on the mix of cases we chose and should not be read as expected rates on real tasks; the case-level outcomes are the informative part. The seven false completions each trace to a specific gap in $\Phi$:
\begin{itemize}
\item \emph{Wrong query (S7).} A results page for a different query passes, because the search check only asks whether the URL is a results page.
\item \emph{Soft errors (N6, N7).} A ``page not found'' message without a status code in the title, and a redirect to a login page, pass; neither is in the error vocabulary. The DOM extractor classifies login and error pages separately, but $\Phi$ does not consult that classification.
\item \emph{Unlisted challenge (C4).} An interstitial whose text contains none of the 12 challenge phrases passes.
\item \emph{Substring match (T4).} ``Meeting at 10am tomorrow'' satisfies a request to enter exactly ``Meeting at 10am''.
\item \emph{Length as a proxy for content (X4).} Any answer longer than 40 characters that does not start with a navigation verb counts as an extraction, even if it lacks the requested fact. Because the planner's own \texttt{reasoning} string on a \texttt{complete} action becomes the answer, a verbose planner can satisfy this check by itself.
\item \emph{Step status from dispatch (P3).} A click that dispatched on the wrong element marks its step complete, so the plan check passes.
\end{itemize}
The single false rejection (X6) is the mirror image of X4: a correct answer of 13 characters is rejected by the length threshold. Each of these gaps corresponds to a check that can be added without a model call (query comparison, reuse of the page-state classifier, exact match for exact-text requests, answer-to-goal term overlap, and step predicates derived from the planner's expected outcome), and the fixture set is designed to serve as a regression suite for them.

The gate is cheap relative to model inference. On a 4-core Intel Xeon (2.8\,GHz) container with Chromium~141 in headless mode, the median time for one full decision (CAPTCHA pre-check plus $\Phi$) over 20 repetitions per case was 33.8\,ms, with a maximum per-case median of 52.5\,ms; decisions that stop at the URL-based CAPTCHA check took under 8\,ms. Most of the time is spent reading page content and title through the browser protocol.

\subsection{Routing Behavior}

Table~\ref{tab:route} shows which model the router selects for each call type the agent issues, evaluated without inference for two sets of installed models. With the launcher's default installation, every text call resolves to \texttt{qwen2.5:1.5b}, three of them through the fallback chain, so role-based routing reduces to a single text model and a vision model. With all configured models installed and each call routed in isolation, each role receives its preferred model. When the calls are issued in the order the agent issues them, passing the previously selected model as the active one, stickiness keeps the lightweight model chosen for intent parsing (\texttt{deepseek-r1:1.5b}) for task decomposition and multi-step planning, because the router's capability profile lists it as able to plan. Only recovery, which is exempt from stickiness, and image inputs switch models. Stickiness thus saves model loads at the cost of never using the planner model in a normal run. Whether that trade is worth making is an empirical question for the ablations of Section~\ref{sec:setup}.
