\section{Results and Discussion}
\label{sec:results}

\subsection{Completion Gate on Constructed End States}

Table~\ref{tab:gate} reports the gate study. Of the 22 end states that do not satisfy their goal, the gate withholds completion in 15: all three search-engine home pages, all three pages with an HTTP error code in the title, three of the four bot-check pages (halted as \textsc{Blocked}), an empty and a wrong text field, three incomplete extraction answers including one produced while still on the search home page, and a plan with a pending step. The dispatch-only rule reports all 22 as complete. Among the 13 satisfied end states, the gate rejects one.

\input{tables/gate_results}

The FCR values depend on the case mix we chose and are not expected rates on real tasks; the case-level outcomes are the informative part. Each of the seven false completions traces to a specific gap in $\Phi$. A results page for a different query passes, because the search check only asks whether the URL is a results page (S7). A ``page not found'' message without a status code in the title and a redirect to a login page pass (N6, N7); the DOM extractor classifies such pages, but $\Phi$ does not consult that classification. An interstitial containing none of the 12 known challenge phrases passes (C4). ``Meeting at 10am tomorrow'' satisfies a request to enter exactly ``Meeting at 10am'', because matching is by substring (T4). Any answer over 40 characters that does not begin with a navigation verb counts as an extraction even without the requested fact (X4); since the planner's own \texttt{reasoning} string on a \texttt{complete} action becomes the answer, a verbose planner can satisfy this check by itself. Finally, a click dispatched on the wrong element marks its step complete, so the plan check passes (P3). The one false rejection (X6) mirrors X4: a correct 13-character answer fails the length test. Every gap maps to a check that needs no model call (query comparison, reuse of the page-state classifier, exact matching, answer-to-goal term overlap, step predicates from the planner's expected outcome), and the fixtures can serve as a regression suite for them.

The gate is cheap relative to model inference. On a 4-core Intel Xeon (2.8\,GHz) container with Chromium~141 in headless mode, the median time for one full decision (CAPTCHA pre-check plus $\Phi$) over 20 repetitions per case was 33.8\,ms, with a maximum per-case median of 52.5\,ms; decisions that stop at the URL-based CAPTCHA check took under 8\,ms. Most of the time is spent reading page content and title through the browser protocol.

\subsection{Routing Behavior}

Table~\ref{tab:route} shows the router's selection per call type, computed without inference. With the launcher's default installation, every text call resolves to \texttt{qwen2.5:1.5b}, three of them through the fallback chain, so routing reduces to one text and one vision model. With all configured models installed, isolated calls each receive their role's preferred model. In the agent's actual call order, however, stickiness keeps the lightweight model chosen for intent parsing (\texttt{deepseek-r1:1.5b}, whose profile lists planning) for decomposition and multi-step planning; only recovery, which is exempt, and image inputs switch. Stickiness saves model loads at the cost of never reaching the planner model, a trade the single-model ablation can quantify.

\subsection{Test Suite}

Table~\ref{tab:tests} summarizes the repository's tests. All passing tests run without a language model: node tests call graph nodes directly with the executor and gateway stubbed, no test runs the compiled graph, and the two passing end-to-end tests accept a failed task as well as a completed one. Of the four failures, two need Ollama, one times out waiting on a browser page and one needs scripts missing from the repository; the collection error is a missing import under Python~3.11. The suite supports claims about component behavior (CAPTCHA blocking, routing rules, checkpointing), not about task success.
