\section{Security, Privacy and Ethical Considerations}
\label{sec:security}

\paragraph{Threat model} We consider (i)~instructions embedded in page content that try to redirect the agent~\cite{greshake2023indirect}; (ii)~high-impact actions such as posting, sending or purchasing without consent; (iii)~damage to the local system once file and process actions exist; and (iv)~disclosure of user data to unintended parties. The user and the host are trusted; websites are not. A compromised host or model is out of scope.

\paragraph{Current mitigations} A sanitizer replaces 17 patterns of instruction-override, delimiter, exfiltration and role-manipulation phrasing in element text, labels and placeholders before they reach the planner. Before navigation, a risk gate pauses tasks whose parsed action is posting, e-mailing, purchasing, deleting or transferring, or whose risk level is high or critical, and asks the user. The intent and risk level are derived from the user's request alone, before any page is read, so page content cannot lower them. The service listens on loopback, every model call is logged with destination and payload sizes, and credential-like values are scrubbed from broadcast events.

\paragraph{Gaps} The sanitizer is a fixed denylist; systematic evaluations find existing prompt-injection defenses insufficient~\cite{liu2024formalizing}, and paraphrased or encoded instructions do not match its patterns. Page title, URL, extracted text, memory records and screenshots are not filtered. Both the action label and the risk level that trigger approval are free text chosen by a small model, and the intent prompt does not offer all the labels the gate checks for. Approval is decided once per task: no individual action is re-assessed after page content has been read, so an injected instruction that steers the planner to submit a form is not gated. The API has no authentication; the loopback binding and a localhost-only CORS policy limit, but do not control, who can call it. The audit log covers model calls but not browsing, and its locality flag is a substring test that is logged, not enforced. The privacy property we claim is therefore narrow: \emph{by default, model inference runs on the user's machine and no prompt or screenshot is sent to a model provider.} Data the user asks the agent to enter on a website still leaves the machine, and typed text is stored in clear locally. The desktop design addresses several of these gaps with deterministic tiers, per-action and action-bound approvals, and a hash-chained audit log.

\paragraph{CAPTCHAs and automation etiquette} On a CAPTCHA or bot check the agent stops, marks the task \textsc{Blocked} and keeps the browser open; the user can solve the challenge and resume (refused while it is still present) or restart the search on another engine, which loads its result URL directly. There is no solver. The browser does, however, disable automation-detection features, send a fixed desktop user-agent string, and hide \texttt{navigator.webdriver}; on Google it types queries instead of loading result URLs; and the DOM extractor writes identifier attributes into every page, which sites can observe. These measures make the agent look like a person using a browser. We consider them acceptable only for a personal assistant acting at human pace on its user's own requests, never for bulk access, and we recommend that deployments disable them wherever a site's terms prohibit automated access. Chromium also runs with its sandbox disabled; re-enabling it is a simple hardening step.
